# WRIC chart-SPR search counter baseline (Phase 0)

This file is the **Phase 0 baseline snapshot** of `chart_spr_search_counters`
for the DAG-native SPR plan.  It captures one deterministic search run on
`data/test_5_trees/` in the current conservative `rebuild_after_accept = true`
mode, so every later phase can diff a fresh run's counters against it and
detect regressions (e.g. "full rebuild per accept", "dense materialize per
candidate", or a renamed counter hiding either).

The snapshot is intentionally **counter-only**: timing fields
(`total_ms`, `local_scoring_ms`, `cache_build_ms`, ...) are machine-dependent
and are deliberately omitted so the baseline diffs cleanly across machines and
CI runs.

## How to regenerate

The snapshot is produced by `tools/wric_counter_baseline.cpp`, a one-shot
generator that emits **only the fenced snapshot block below** (not this prose).
It is intentionally **not** a run-target; it *is* covered by the compile-only
ctest `wric_counter_baseline_compiles`, so a renamed counter field breaks CI
before it breaks regeneration.

**Do not redirect the generator over this file** (`./build/wric_counter_baseline
> doc/WRIC-CHART-SPR-SEARCH-COUNTER-BASELINE.md`): the generator's output is the
~70-line snapshot block only, so that would silently delete the hand-written
prose.  Instead, use `tools/regen_counter_baseline.sh`, which splices the
generator's stdout between the `<!-- wric-counter-baseline: snapshot begin/end
-->` markers that wrap the fenced block below, leaving every line of prose
untouched.  Build the generator once, then regenerate:

```sh
# 1. Ensure the larch library and generated headers exist.
cmake -B build -DGCC_TOOLCHAIN=$HOME/install/gcc-trunk -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

# 2. Compile the generator with the project's flags.
g++-trunk -std=c++26 -freflection -I include -I build/generated \
    tools/wric_counter_baseline.cpp build/liblarch.a -lz -lpthread \
    -static-libstdc++ -static-libgcc -o build/wric_counter_baseline

# 3. Splice the freshly generated snapshot block into this doc (prose preserved).
./tools/regen_counter_baseline.sh
```

The run is deterministic: serial local scoring (`local_score_worker_count = 1`,
the option default) and a fixed `seed = 1`, so two runs on the same commit
produce byte-identical counters and the splice is idempotent.

## Configuration

- **Fixture:** `data/test_5_trees/tree_0.pb.gz .. tree_4.pb.gz`, merged.
- **Polytomy mode:** `expand_soft_bounded`, `max_shapes_per_polytomy = 1`.  The
  merged DAG contains soft polytomies, so chart search requires a
  binary-chart-compatible grammar; this mirrors the `dagutil_chart_spr_search`
  ctest configuration for this fixture.
- **Search mode:** `rebuild_after_accept = true` (conservative Phase-5 path:
  materialize each accepted move and rebuild the grammar/pattern/chart sidecar).
- **Acceptance / selection:** `exact_multisite` / `lower_bound_top_k` (the
  `chart_spr_search_options` defaults).
- **Iterations:** `max_iterations = 3`, `seed = 1`.

## What later phases check against this baseline

Per the plan's cross-cutting counter contract:

- **Phase 4** asserts that a local-commit run (`rebuild_after_accept = false`)
  keeps `sidecar_rebuilds_after_accept == 0` and
  `overlay_materializations_for_accept_materialization == 0`; the umbrella
  `full_overlay_materializations` may still be nonzero because exact candidate
  verification materializes overlays (Phase 9's transient path reduces this for
  committable candidates but tombstone-scope cold fallbacks still materialize;
  see the Phase-9 caveat in `WRIC-SPR-SEARCH.md`).
- **Phase 4** also asserts conservative mode (`rebuild_after_accept = true`)
  passes its existing tests unchanged and that its per-accept materialization
  count is unchanged from this baseline.
- **Phase 5** adds one separately counted
  `overlay_materializations_for_final_compaction` to local-commit runs when the
  dense chain materialization lands in grammar-valued compaction; this baseline
  pins the conservative-mode reference for that comparison.
- **Phase 10** diffs a local-commit run's counters against this baseline in a
  CI-scale sanity table.

Note: on this particular fixture the search accepts **no** moves
(`accepted_moves == 0`), so the accept-path counters
(`overlay_materializations_for_accept_materialization`,
`sidecar_rebuilds_after_accept`) are zero here.  They become nonzero on
fixtures where an improving move is found; later phases that need a
post-accept baseline should capture a supplementary snapshot on such a fixture
(e.g. one of the tiny improving-move fixtures in
`test/chart_spr_search_test.cpp`).
